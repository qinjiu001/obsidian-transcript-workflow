# WorkBuddy 播客文稿处理交接文档

## 先做什么

你的任务是把本地英文播客 DOCX 全文稿，整理成可长期保存在 Obsidian 中的简体中文 Markdown 文章。

每次默认只处理一篇。开始前必须：

1. 确认能够读取源 DOCX、Human SOP、迭代记录和目标目录；
2. 读取当前 Human SOP；
3. 扫描实时待处理队列；
4. 确认目标文件尚不存在；
5. 完整读取源 DOCX 后再写文章。

不要只生成几百字摘要，不要逐句翻译，不要生成 HTML，不要执行额外美化。

## 一、当前有效文件与路径

### 当前 Human SOP

```text
<OBSIDIAN_VAULT>\raw\01-articles\Human_SOP_标准化模板.md
```

Human SOP 是当前有效的人工目标和验收规则。历史版本和试验过程不覆盖当前 Human SOP。

### 迭代记录

```text
<OBSIDIAN_VAULT>\迭代记录.md
```

迭代记录保存历史问题、截图和每次 Agent 执行反馈。迭代记录中的新想法只有经过人工确认并写入当前 Human SOP 后，才成为永久规则。

### 源文稿根目录

```text
<SOURCE_ROOT>
```

### Obsidian 成品根目录

```text
<OBSIDIAN_VAULT>\raw\02-papers
```

必须镜像保留源文件的相对分类目录。

映射规则：

```text
SOURCE_ROOT\<相对分类目录>\<文件名>_原文.docx
    →
TARGET_ROOT\<相对分类目录>\<文件名>_Obsidian笔记.md
```

### 可参考的合格成品

```text
<OBSIDIAN_VAULT>\raw\02-papers\增长\增长-红人于联盟营销\002__Bonus：九位数品牌增长案例_Obsidian笔记_第二版.md
```

这份文件用于理解内容深度、证据边界和正文结构。不要机械复制其中的观点、标题数量或表格数量。

## 二、规则优先级

发生冲突时按以下顺序执行：

```text
用户当前明确指令
> 当前 Human SOP
> 本交接文档
> 已批准的 Skill / Workflow 规则
> 尚未批准的迭代记录
> 历史版本
```

如果当前 Human SOP 与本交接文档冲突，停止采用本交接文档中的旧规则，并在执行反馈中指出冲突。

不要擅自修改 Human SOP、Skill、路径配置或历史迭代记录。发现需要升级的规则时，先写入执行反馈，等待人工确认。

## 三、运行前检查

### 1. 检查工具与文件访问

确认：

- 能读取本地 DOCX；
- 能写入目标 Obsidian 目录；
- 能以 UTF-8 保存 Markdown；
- 能查看目标文件是否已经存在；
- 能运行 Python 时，优先使用下面的队列扫描器。

队列扫描命令：

```powershell
python -X utf8 "<SKILL_DIR>\scripts\scan_transcript_queue.py"
```

如果无法运行该命令，必须手动检查源文件、目标路径和同名输出是否存在，并在反馈中说明队列统计未验证。

### 2. 选择文稿

- 用户指定文件时，只处理指定文件。
- 用户要求继续队列时，选择扫描器输出的第一篇待处理文稿。
- 默认一次只处理一篇。
- 不要一次处理全部 300 多篇文稿。
- 目标文件已经存在时，不要覆盖；停止并询问是跳过还是生成版本文件。

### 3. 当前队列快照

这是交接时的快照，不是永久数字。每次工作前必须重新扫描。


## 四、单篇文稿处理流程

### Step 1：完整读取 DOCX

必须读取完整文档，包括：

- 所有非空段落；
- 标题；
- 表格；
- 时间戳；
- 重要数字；
- 人名、品牌名、产品名；
- 反例和不确定表达。

如果是已经存在的播客全文稿，不要再次运行语音转录。

文档很长时，优先分段完整读取并建立覆盖清单，不要因为篇幅长就主动缩成短摘要。只有确认无法完整读取或无法保持证据覆盖时，才停止并请求人工处理。

### Step 2：建立内部证据清单

写作前先整理：

- 一句话核心主题；
- 所有重要判断，不固定为三个；
- 主要框架、步骤和因果链；
- 重要案例、数字和阈值；
- 对理解结论有影响的反例；
- 可用的短原话；
- ASR 错误、模糊专名和待验证事实；
- 原文直接支持的行动建议。

证据清单用于自检，默认不另存文件。

### Step 3：转写成中文可读文章

目标是重构为自然中文文章，而不是逐句翻译。

必须：

- 删除问候、口头填充、重复、假启动和订阅广告等无信息内容；
- 保留说话人的真实立场、案例、数字和因果逻辑；
- 用自然段解释推理，不要把全文改成项目符号；
- 专业术语首次出现时可保留英文；
- 无法确认的名称和数字必须标记，不得猜测；
- Agent 推演必须放进“我的思考”，不得冒充嘉宾原话；
- 不设置统一字数上限，内容长度服从证据完整度。

### Step 4：生成一个 Obsidian Markdown 成品

只生成一个 `.md` 文件。不要同时生成 Deep、HTML、Excalidraw 或设计说明等重复成品。

YAML 使用以下字段；未知字段可以省略，不要猜测：

```yaml
---
title: "<中文标题>"
aliases:
  - "<短标题>"
source_file: "<源文件名>"
source_path: "<源文件完整路径>"
source_url: "<官方来源，能够确认时填写>"
podcast: "<节目名称>"
episode: "<单集名称>"
guest: "<嘉宾>"
duration: "<时长>"
transcript_segments: <正文段落数>
version: "<仅在版本文件中填写>"
created: YYYY-MM-DD
tags:
  - <主题标签>
---
```

禁止生成：

- `source_type`
- `language`
- `status`
- `human_sop`
- `cssclasses`

正文结构：

```markdown
# 可读的中文标题

> [!summary] 一句话摘要
> 用一句话说明真正主题。

> [!warning] 证据与转录提示
> 说明来源限制、ASR问题、产品主张或待验证事实。

## 背景与问题

## 核心判断
### 判断1
### 判断2
按内容实际需要继续增加，不固定为三个。

## 主要框架或因果链
有真实流程、层级或因果系统时才使用 Mermaid。

## 重要案例与数字

## 指标、决策或对比
有重复可比字段时使用表格。

## 可执行动作或实验
- [ ] 行动项

## 待验证问题

## 短原话

## 可拆分的原子笔记
- [[概念]]

## 关联主题
- [[主题]]

## 我的思考
明确标注为 Agent 推演。
```

不要在摘要后重复生成 `## 基本信息`。节目、嘉宾、时长、来源等只保留在 YAML。

## 五、Mermaid规则

只有内容中存在真实流程、层级、决策或因果系统时才生成 Mermaid，默认最多一张。

WorkBuddy 不得假设能够调用 Codex 的 `mermaid-visualizer`。没有该 Skill 时，直接生成兼容 Obsidian 的安全 Mermaid：

- 默认使用 `flowchart TB`，避免过宽；
- 节点文字使用引号；
- 节点文字不使用 Emoji；
- 不使用 `1. 文本` 这种会触发列表解析的写法；
- 不在普通矩形节点中使用 `<br/>`；
- 不使用 `style A,B` 批量样式，必须逐个节点设置样式；
- 节点标签保持简短；
- 实际打开 Obsidian 验证，不能只检查代码。

如果 Mermaid 无法验证且存在解析错误，优先修复；仍无法修复时删除该图，并把问题写入执行反馈，不能交付损坏图表。

## 六、格式与美化

- 使用用户当前的 Obsidian 主题；
- 不生成 HTML；
- 不嵌入 CSS；
- 不添加 `cssclasses`；
- 不执行第二次美化；
- 不默认生成 Excalidraw；
- 默认最多一张 Mermaid、两张 Markdown 表格；
- 不为了装饰增加没有信息价值的模块。

## 七、验收清单

保存后必须检查：

- [ ] 源 DOCX 已完整读取；
- [ ] 读者不听原播客也能理解；
- [ ] 不是几百字的简单摘要；
- [ ] 重要案例、数字、反例和不确定性没有丢失；
- [ ] Agent 推演与原文观点已分开；
- [ ] YAML 合法并且没有禁用字段；
- [ ] 没有“基本信息”正文区块；
- [ ] 没有 HTML、CSS 或自定义主题类；
- [ ] 核心判断数量由内容决定；
- [ ] Mermaid 在 Obsidian 中正常显示；
- [ ] 表格没有横向严重溢出；
- [ ] 文件保存到 `raw/02-papers` 的正确镜像目录；
- [ ] 没有覆盖现有文件；
- [ ] 队列重新扫描后完成数增加一；
- [ ] 已把 Agent 执行反馈写回《迭代记录》。

## 八、必须停止并询问人工的情况

- 文档无法读取；
- 原文严重缺失；
- 分段后仍无法完整处理长文；
- 无法确认会影响理解的人名、品牌或关键概念；
- 目标文件已存在但用户没有授权覆盖或生成新版本；
- 需要改变 Human SOP、Skill、路径或命名规则；
- 发现当前规则互相冲突；
- 无法访问目标 Obsidian 目录；
- 无法验证关键图表或文件完整性。

停止时必须说明：

1. 卡在哪一步；
2. 已经检查过什么；
3. 缺少什么信息或权限；
4. 人工提供什么以后可以继续。

## 九、每次执行后的反馈回写

完成或停止后，都要在《迭代记录》当前版本下追加一次反馈：

```markdown

- 修改了什么：
- 没有修改什么：
- 验证结果：

### 运行中发现的问题
- 最费时间的步骤：
- 最容易出错的步骤：

- 原规则中缺失的判断：
- Agent做出的临时假设：

### 需要人工确认
- 是否接受这项修改：
- 是否升级为Human SOP：
- 是否同步到Skill：
- 是否存在尚未补充的隐性知识：

### 规则升级状态
- [ ] 只保留在迭代记录
- [ ] 已通过人工验证
- [ ] 已写入Human SOP
- [ ] 已同步到Skill
- [ ] 已完成回归测试
```

不要只在聊天中报告。聊天回复和迭代记录都必须包含本次结果。

## 十、单篇任务交付回复

每篇完成后向用户报告：

- 源 DOCX 路径；
- 成品 Markdown 路径；
- 文档段落数或字符规模；
- 核心判断数量；
- Mermaid 和表格数量；
- 证据或专名风险；
- 队列完成数与待处理数；
- 已完成反馈回写；
- 仍需人工确认的事项。

交付标准不是“文件已生成”，而是文件已经保存、检查、在 Obsidian 中可读，并且运行反馈已进入迭代闭环。
